# AIPE Plugin — proposed architecture

Status: **planned**. No plugin package or `AIPE-Plugin` repository exists yet.
This note records the architecture behind the public `/plugin/` page, so the
future repository starts from the same contract. It is a design note, not an
implementation. The public page deliberately stays product-level (what the plugin
gives access to, how to use AIPE today, what comes next); the layers, Registry
relationships and responsibilities below belong here, not on the website.

## Position in the ecosystem

```text
AIPE-Core                  common engineering language / schema / engineering state
AIPE-Registry              catalogue and discovery layer
AIPE-Plugin (planned)      agent-facing integration layer
Spirit-Connect-AIPE-Labs   human-facing presentation layer (aipe.presentation)
```

Specialist repositories (Semiconductor Database, Magnetics Database, Simulation
Skills, Design Agent, AIPE Sketch, Academy, …) are capabilities. Each remains the
source of truth for its own data, code and skills.

## Interfaces available today

| Interface | Audience | Status |
| --- | --- | --- |
| `https://aipel.co.uk/` | humans | available |
| `https://aipel.co.uk/aipe.md` | agents (zero-install fallback) | available |
| `https://aipel.co.uk/aipe.json` | machines | available |
| AIPE Plugin | agents | planned |
| Registry API / CLI | machines | planned |

`aipe.md` and `aipe.json` are generated by AIPE Registry from validated
`aipe.yaml` manifests and published unchanged by this site. They stay available
after the plugin ships: `aipe.md` is the public, agent-readable Registry interface
and the fallback for agents that cannot install anything.

## Responsibilities

```text
Coding agent (Codex, Claude Code, …)
    ↓
AIPE Plugin   router · discovery · capability loader · orchestrator
    ↓
AIPE Registry (aipe.json)
    ↓
AIPE Core     engineering state, evidence, units
    ↓
Data / Models / Designs / Tools & Agents / Labs   (canonical repositories)
```

1. **Router** — recognise the engineering task in the user's project and decide
   which capability types could help.
2. **Discovery** — query the Registry by type, domain, maturity, integration and
   tool requirements; surface stated limitations before use.
3. **Capability loader** — fetch the specific skill folder, tool interface or
   dataset adapter from its canonical repository at a pinned revision.
4. **Orchestrator** — sequence capabilities through Core engineering state so
   assumptions, evidence and results stay reviewable.

## Constraints

- Thin: the plugin contains no copies of specialist repositories.
- One source of discovery: it reads the same Registry output as the website.
- Works in the user's existing project and tools; no separate platform.
- Never upgrades a maturity or validation claim; it reports what the Registry says.

## Existing building blocks

AIPE Simulation Skills already packages workflows as agent-loadable folders:
`SKILL.md` (workflow), `references/` (loaded on demand) and `agents/openai.yaml`
(agent metadata). Its README documents installation into a Codex skills
directory. Installing these folders as Claude Code skills has not yet been
validated, and the website says so.
